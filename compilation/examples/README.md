# Пояснения к примерам практического занятия 4

Это руководство к архиву `lecture-4-examples` (`Ex1`–`Ex6`). По каждому примеру
сказано, что нужно запустить и что при этом ожидается, и что этот пример
показывает. Все команды выполняются из каталога соответствующего примера
(`cd Ex1`, `cd Ex2`, …). Для сборки используется `gcc`.

## Подготовка: как собирать и смотреть на результат

Набор команд, которыми мы будем пользоваться:

```bash
gcc --save-temps hello.c -o hello   # сохранить промежуточные файлы (.i, .s, .o)
gcc -E hello.c -o hello.i           # остановиться на препроцессировании
gcc -c hello.c -o hello.o           # только объектный файл
objdump -d hello.o                  # дизассемблировать
objdump -s -j .rodata hello.o       # показать секцию констант
nm hello.o                          # таблица символов
gcc -Wall -Wextra -Wpedantic hello.c -o hello   # предупреждения
gcc -Wall -Werror hello.c -o hello              # предупреждения как ошибки
```

Напоминание о секциях объектного файла: 
- `.text` — исполняемый код (функции и вызовы, переведённые в машинный код);
- `.bss` — неинициализированные глобальные и статические переменные;
- `.rodata` — константы.

Символы в `nm` помечаются
заглавными (`T`, `D`, `B`, `R`) для глобальных и строчными (`t`, `d`, `b`, `r`)
для локальных; `U` — символ используется, но здесь не определён, его адрес должен
подставить линкер.

## Ex1: константы и секции

Программа печатает строку, подставляя в неё строковую константу `"September"` и
числовую `25`.

**Запустите:**

```bash
cd Ex1
gcc --save-temps hello.c -o hello
./hello
```

**Ожидаемый результат:** `Hello world! Today is September 25.` Рядом появятся
`hello.i`, `hello.s`, `hello.o` — промежуточные стадии.

Дальше посмотрите, где что лежит:

```bash
objdump -d hello.o
objdump -s -j .rodata hello.o
```

**Ожидаемый результат.** В дизассемблированном `.text` числовая константа видна
прямо в коде как непосредственное значение: `mov $0x19,%edx` (`0x19` — это 25).
В секции `.rodata` лежат строки `"September"` и `"Hello world! Today is ..."`, а
обращения к ним идут через адреса (команды `lea`). То есть строковые константы
попадают в `.rodata`, а числовая может оказаться прямо в коде; если бы число было
объявлено как `const`-переменная, оно тоже ушло бы в `.rodata`.

В этом же выводе видно, что `printf` вызывается командой `call` и остаётся
неразрешённым (`U`) символом, а линковка по умолчанию динамическая: стандартную
библиотеку в файл не встраивают, если специально не попросить.

## Ex2: аргументы командной строки и проверка ввода

Здесь две программы: `Ex2` — с ошибками, `Ex2_fixed` — исправленная.

**Запустите `Ex2` и сравните с ожидаемым:**

```bash
cd Ex2
gcc hello.c -o hello
./hello                 # программа ждёт одного аргумента (argc == 2)
./hello 28
```

**Ожидаемый результат.** Без аргументов печатается `Error!` и возвращается код
22. С одним аргументом (`./hello 28`) печатается
`Hello world! Today is ./hello 28.` — то есть в текст подставились имя программы
(нулевой аргумент) и единственный переданный аргумент. Ошибки примера: условие
должно быть `argc == 3`, а обращаться нужно к `argv[1]` и `argv[2]`, потому что в
`argv[0]` лежит имя (путь) вызванной программы, а `argc` на единицу больше числа
содержательных аргументов.

**Запустите `Ex2_fixed`:**

```bash
cd ../Ex2_fixed
gcc hello.c -o hello
./hello September 28    # корректный ввод
./hello 28 September    # аргументы перепутаны
./hello September 40    # дата вне диапазона
./hello                 # нет аргументов
echo $?                 # код возврата последней команды
```

**Ожидаемый результат:**

- `./hello September 28` → `Hello world! Today is September 28.`, код возврата 0;
- `./hello 28 September` → `Error: Invalid input format!` (первый `sscanf` на
  `%s` берёт `28`, а второй `%d` уже не может прочитать слово-месяц);
- `./hello September 40` → `Error: Date must be between 1 and 31!`;
- `./hello` без аргументов → `Error!`.

При ошибке программа возвращает ненулевой код (`-EINVAL`, «недопустимое
значение» из `errno.h`; в оболочке это видно как 234). Функция `sscanf`
возвращает число успешно преобразованных элементов: раз в строке формата один
спецификатор, правильным считается возврат 1. Вместо `-EINVAL` можно возвращать,
например, `-1`, если программа не различает ошибки, либо собственные коды. После
чтения дата проверяется в диапазоне 1–31; соответствие месяца числу дней
специально не проверяется.

## Ex3: программа из нескольких файлов

`Ex3` — «сломанная» версия: `main.c` вызывает `distance`, но не подключает её
заголовок. `Ex3_fixed` — исправленная.

**Запустите сборку `Ex3` и посмотрите на ошибку:**

```bash
cd ../Ex3
gcc -c main.c -o main.o
```

**Ожидаемый результат:** ошибка компиляции
`implicit declaration of function 'distance'` — компилятор видит только свой
файл. Исправление — добавить в `main.c` строку `#include "distance.h"`
(локальные заголовки подключаются кавычками, системные — угловыми скобками).
После этого соберите модули, посмотрите таблицу символов и слинкуйте:

```bash
gcc -c main.c -o main.o
gcc -c distance.c -o distance.o
nm main.o          # T main, U distance, U printf, ...
nm distance.o      # T distance, t abs
gcc main.o distance.o -o prog
./prog 10 3
./prog
```

**Ожидаемый результат.** В `distance.o` символ `abs` помечен строчной `t`: он
локальный, потому что в заголовке объявлен как `static` (и `inline`). Свой `abs`
в `Ex3/distance.h` реализован неверно — при отрицательном аргументе возвращает
сам аргумент, а не его модуль, поэтому `./prog 10 3` печатает `-7` вместо `7`.
Запуск `./prog` без аргументов даёт segmentation fault: в `main.c` нет проверки
`argc`, а `sscanf` вызывается с `argv[1]` и `argv[2]`.

**Соберите исправленную версию:**

```bash
cd ../Ex3_fixed
gcc -c main.c -o main.o && gcc -c distance.c -o distance.o && gcc main.o distance.o -o prog
./prog 10 3     # 7
./prog          # Segmentation fault
```

Здесь собственный `abs` убран и используется стандартный из `<stdlib.h>`, поэтому
результат верный. Segmentation fault остаётся: проверку числа аргументов и
возвращаемого значения `sscanf` надо добавить. Обратите внимание: проверять
`argv[1] != NULL` бесполезно — после успешной проверки `argc == 3` элементы
`argv[1]` и `argv[2]` всегда ненулевые указатели, даже если в них строка `"0"`.
Правильный путь — проверять `argc` и возврат `sscanf`.

**Заголовок в подкаталоге (`Ex3_subdir`):**

```bash
cd ../Ex3_subdir
gcc -c main.c -o main.o           # fatal error: distance.h: No such file or directory
gcc -I dist -c main.c -o main.o   # теперь находится
gcc -c dist/distance.c -o distance.o
gcc main.o distance.o -o prog
./prog 3 10                        # 7
```

**Ожидаемый результат.** Первая команда не находит заголовок. Исправить можно
двумя способами: указать путь прямо в `#include` (`"dist/distance.h"`) или
добавить каталог поиска ключом `-I dist`. Для сборки самого `dist/distance.c`
ключ `-I` не нужен — его заголовок лежит рядом с ним.

## Ex4: макросы и скобки

В примере два похожих макроса: `abs1(x)` — это `x > 0 ? x : -x`, а `abs2(x)` —
`((x) > 0 ? (x) : (-x))`. Разница в скобках.

**Запустите:**

```bash
cd ../Ex4
gcc -E main.c | tail -25    # посмотреть, во что раскрываются макросы
gcc main.c -o main && ./main
```

**Ожидаемый результат.** `gcc -E` показывает, что `x + abs1(y)` раскрывается как
`(x + y) > 0 ? y : -y` — из-за отсутствия скобок арифметика считается не в том
порядке. При значениях из примера (`x = 7`, `y = -8`) первое выражение даёт 8,
второе — 15, поэтому программа печатает `Error: 8 != 15`. Если подставить нули,
результаты совпадут и сообщения не будет: расхождение возникает, когда при
сложении меняется знак.

**Попробуйте** поменять `x` и `y` в исходнике, пересобрать и убедиться, что
сообщение появляется не всегда. Во `abs2` скобки сохраняют нужную группировку —
именно так и надо писать макросы. Препроцессированный код особенно полезен, когда
макросы определяют структуры данных для эмуляции дженериков: читать раскрытый
текст проще, чем догадываться по исходнику.

## Ex5: оптимизации, псевдонимы и Compiler Explorer

`sum.c` — самостоятельная программа: читает два числа с плавающей точкой и
печатает их сумму.

**Запустите:**

```bash
cd ../Ex5
gcc sum.c -o sum
printf '1.5 2.25\n' | ./sum
```

**Ожидаемый результат:** `3.750` (формат `%.3f` — три знака после запятой).

Основная часть примера разбирается в Compiler Explorer (`godbolt.org`). Откройте
его, переключите язык с C++ на C и, вероятно, отключите интеловский синтаксис
ассемблера, чтобы не путать его с AT&T. Compiler Explorer подсвечивает, из какой
части исходника получилась каждая инструкция; уровень оптимизации задаётся в
поле компиляторных опций, а при наведении на инструкцию видно её описание.
Сравните `-O0` и `-O1` на небольшой функции с локальной переменной: без
оптимизаций видно много работы со стеком (значение локальной переменной лежит на
стеке), а с `-O1` неиспользуемое присваивание выбрасывается, и остаётся, по сути,
умножение и перекладывание результата в `EAX`. В ассемблере встречаются суффиксы
вроде `q` или `l` (`pushq`, `movl`) — это размер операнда, а сама команда — тот
же `push`, что разбирался на лекции.

Отдельно разберите `restrict.c`, где есть `arr_copy` и `arr_copy_restrict`.
Указатели `from` и `to` могут указывать в одну память, и это мешает оптимизации;
`restrict` сообщает компилятору, что области не перекрываются.

**Соберите `restrict.c` с оптимизацией и посмотрите на результат:**

```bash
gcc -O2 -c restrict.c -o restrict.o
objdump -dr restrict.o
```

**Ожидаемый результат.** В дизассемблированном `arr_copy_restrict` видно
`shl $0x2` (умножение числа `int` на размер `int` через сдвиг) и вызов `memcpy` —
при `-O2` компилятор понял, что весь цикл копирования сводится к `memcpy`, хотя в
исходнике его не было. Аргументы едут в регистры `RDI`/`RSI`, длина — в `RCX`.
Если не сказать компилятору, под какое железо собирать, он может пытаться
векторизовать код под обобщённую архитектуру.

## Ex6: предупреждения компилятора

Три короткие программы, показывающие разные группы предупреждений.

**Запустите и сравните:**

```bash
cd ../Ex6
gcc -Wall warn.c -o warn
gcc -Wall -Werror warn.c -o warn
gcc -Wall wextra.c -o w
gcc -Wall -Wextra wextra.c -o w
gcc -Wall wpedantic.c -o w
gcc -Wall -Wpedantic wpedantic.c -o w
```

**Ожидаемый результат:**

- `warn.c` с `-Wall` — два предупреждения: `suggest parentheses around assignment
  used as truth value` (в условии `if (a = b)` вместо `==`) и `unused variable` для
  переменной `d`. С `-Werror` оба становятся ошибками, исполняемый файл не
  создаётся. Скобки вокруг присваивания — способ явно сказать, что нам нужен
  результат присваивания; неиспользуемая переменная часто указывает на опечатку
  или забытую переменную.
- `wextra.c` с `-Wall` компилируется молча, а с `-Wextra` появляется
  предупреждение о сравнении знакового и беззнакового значений
  (`signed`/`unsigned`). Именно поэтому `-Wall` и `-Wextra` нужно использовать
  вместе.
- `wpedantic.c` (массив нулевого размера) с `-Wall` даёт только предупреждение о
  неиспользуемой переменной, с `-Wextra` — ничего, а с `-Wpedantic` — `ISO C
  forbids zero-size array`. Массив размера 0 стандарт C запрещает: код может
  скомпилироваться, но результат без чёткого задания непредсказуем.

Отдельно запомните про знаковые и беззнаковые типы: `unsigned char` хранит
значения до 255, а `signed char` — примерно от −128 до 127. Если присвоить
беззнаковому значению знаковую переменную (или наоборот), часть значений можно
потерять, о чём и предупреждает компилятор.

И замечание про терминологию: профессиональные термины нужно употреблять
правильно, в том числе склонять слово «байт» (например, «шесть байтов»). За
неуважение к профессиональным терминам на зачёте снижают оценку.
